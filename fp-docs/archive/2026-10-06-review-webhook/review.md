# pi 驱动的代码评审 Webhook 服务 — 开发设计评审

## 评审结论

建议**有条件通过**。设计把范围压得很实：一条 HTTP 路由、一次 pi 调用、零持久化、零跨请求状态，六个架构决策全部终态且都有来源。主要依据是主线闭环完整——触发、处理、失败收束和验证方案都能一一对应，没有悬空章节。

需要评审者确认的条件有两条，都不阻塞进入计划阶段，但必须在实现前表态。第一，接口在 GitLab 原生 webhook 场景下会返回 400，因为 payload 不含代码；这是已确认的边界，评审时要确认产品上接受。第二，同步返回意味着单次请求占用连接 30 秒到 120 秒，评审时要确认调用方接受这个等待。

| 评审面 | 结论 | 设计依据 |
| --- | --- | --- |
| 决策 | 共 6 项；阻塞 6 / 非阻塞 0；全部终态 | `design/backend.md` 第一部分 |
| 数据 | 无持久化，不引入数据模型 | `design/backend.md#设计范围适用性` 数据模型行 |
| 接口 | 新增 1 条路由，5 种状态码 | `design/backend.md#接口权限与兼容边界` |

| 不做事项 | 不回写 GitLab、不做异步与结果存储、不做仓库级 prompt、不做通知、不做 Dashboard、不兼容 GitHub 与 Gitea、不做鉴权 | `proposal.md#out-of-scope` |

## 业务和技术主线

变更触发来自两处：调用方直接 POST 代码，或调用方 POST 一个带 `code` 字段的 GitLab payload。

处理顺序固定为五步：校验请求体与 `code`，组装上下文（GitLab payload 时追加元数据），读取 prompt 文件全文，调用 pi 适配层执行一次评审，取回最终文本。状态变化只发生在单个请求的局部变量与一个内存会话内，服务本身无状态。

结果是同步返回的 200 与 `{"review", "model", "duration_ms"}`。失败分成四条互斥收束：入参不合法 400，prompt 文件不可用 500，pi 调用抛错或文本为空 502，超时 504。

最简单可行方案就是这条链路本身，没有队列、缓存、数据库或跨请求共享状态。复用点是 Express 5 的请求体解析与错误响应，以及 pi SDK 的会话与模型能力。新增依赖只有 Express 5 与 pi SDK；新增配置只有五项环境变量。新增复杂度的必要性由各决策 owner 持有，主线只做链接。

## 状态、并发和执行流程

状态入口只有一处，即 `POST /review/webhook`。服务无状态，一次评审的全部状态活在单请求的局部变量与一个 pi 内存会话里，请求结束即释放。

并发由 Express 默认行为承担，每个请求使用自己的 pi 会话，会话之间不共享可变状态。隔离工作目录在适配层构造时创建一次并在进程内复用，避免每请求产生临时目录。

执行顺序与失败收束严格互斥：入参校验失败立即返回 400，不读文件、不调 pi；prompt 读取失败返回 500，不调 pi；pi 阶段正常拿到非空文本返回 200，抛错或空文本返回 502，信号中断返回 504。超时由 `AbortSignal.timeout()` 驱动，适配层注册一次性 abort 监听并在触发时释放会话，会话释放在 `finally` 中用标志位保证只执行一次，避免信号与正常结束重复释放。

可观察结果有两个：成功响应的 `duration_ms` 反映单次评审耗时，失败响应的 `error` 字段区分三类原因。

评审时要确认超时路径的释放语义没有竞态，这是本设计中唯一需要并发推理的地方。

## 接口、权限和旧入口隔离

| 接口/入口 | 主键或资源 | 权限 | 兼容或隔离边界 | 设计依据 |
| --- | --- | --- | --- | --- |
| `POST /review/webhook` | 无资源标识，请求体 `code` 为唯一必填输入 | 不鉴权 | 全新接口，无旧入口需要隔离 | `D-003`、`P-006` |

请求体接受三个字段：必填的 `code`（代码或 diff 文本），可选的 `context`（额外上下文），可选的 `object_kind`（存在时按 GitLab payload 处理）。响应状态码为 200、400、500、502、504，错误体统一为 `{"error": string}`。

权限按已确认决策不校验调用方身份，服务默认只监听 `127.0.0.1`。这是本次唯一的安全边界，设计没有再叠加任何机制。

需要评审者特别注意兼容边界的表述：GitLab payload 是上下文来源而不是代码来源。GitLab 原生 webhook 单独打本接口会因为请求体没有 `code` 而返回 400。这是已确认的设计边界而非缺陷，但它是本次最容易被误认为 bug 的行为，错误信息必须写明原因。

## 主要风险、迁移、发布和验证

### 主要风险

| 具体失败场景 | 影响 | 预防或处理 | 设计依据 |
| --- | --- | --- | --- |
| pi 按工作目录发现 `AGENTS.md`、skills 或 `APPEND_SYSTEM.md` 并混入系统提示 | 评审结论被无关上下文污染且难以察觉 | 空白临时目录作 `cwd`，覆盖两处 system prompt 来源，关闭全部工具 | `D-002` |
| pi SDK 升级导致会话或资源加载接口变化 | 适配层编译失败或评审行为改变 | 适配层是唯一接触 pi SDK 的模块，接口面收在一个文件 | `D-002`、`D-005` |
| 同步等待期间 GitLab 原生 webhook 因约 10 秒超时重试 | 同一变更被重复评审，浪费模型额度 | 本次不把 GitLab 原生 webhook 作为使用方式，接口文档写明 | `D-004`、proposal 风险 ② |
| 进程内没有可用的 pi 模型凭证 | 每次评审都返回 502 | 启动不做凭证探测，由 README 写明前置条件 | proposal Impact |
| 接口无鉴权且被改绑到外网 | 任何能访问端口的人都消耗模型额度 | 默认只绑 `127.0.0.1`，改 `HOST` 属显式决定 | `P-006` |

有意延后项有三项，均在设计唯一 owner 中记录内容、理由、适用上限、可验证升级触发条件与升级方向。一是并发上限：当前不限流，上限是同时评审数不超过模型并发配额，触发条件是出现排队、模型侧 429 或超时比例上升，升级方向是加信号量。二是 GitLab 只读 API 拉取 diff 与异步评审：当前不做，上限是调用方能接受 120 秒内同步等待，触发条件是需要 GitLab 原生 webhook 直接触发，升级方向是新增 GitLab 客户端与结果查询接口。三是评审模型选择：当前不提供选模型配置，上限是全局共用 pi 设置里的一个模型，触发条件是需要按仓库或按评审等级换模型，升级方向是接入 pi 的模型解析能力。评审时要确认这三项延后都没有削减当前验收、隔离或安全边界。

### 迁移与发布

无 schema 变化、无数据迁移、无兼容窗口，因此没有回滚数据的问题。发布即首次部署，回滚即停掉进程。上线后需要观察的信号是 502 与 504 的出现比例：前者指向凭证或模型配置，后者指向超时上限与实际评审耗时不匹配。

## 评审顺序与抽查路径

1. 先看 `design/backend.md#接口权限与兼容边界`，因为 GitLab payload 不含代码这一条最容易被误判为缺陷，且它决定产品的可用范围。
