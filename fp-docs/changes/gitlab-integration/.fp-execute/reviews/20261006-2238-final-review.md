### Medium

**F-001：changes 重试后仍为空时，管线继续汇总并回写，可能把无意义的评论发到 MR**

- Severity: Medium
- Evidence: `src/gitlab-client.ts:106-115` 三次重试后仍为空返回 `[]`（只 warn 不抛错）；`src/pipeline.ts:73-74` 对空数组分批得到 0 批；`src/pipeline.ts:76-106` 批次循环直接跳过；`src/pipeline.ts:111-117` 仍以空串 `batchResults.join("\n\n---\n\n")` 调用汇总并继续 `postMergeRequestNote`。
- Failure scenario: GitLab 在 3×10s 重试内持续返回空 `changes`（diff 未生成或 MR 无可见 diff）→ 服务把「模型对空输入的汇总回复」当作评审结论回写到真实 MR，产生一条误导性评论。
- Source requirement: design「失败收束」约定「拉取失败…记录日志并结束该任务」；空变更在重试耗尽后等价于拉取失败，当前实现未按此收束。
- Suggested fix: `run()` 拉取后增加 `if (changes.length === 0) { logger.warn("变更列表为空，跳过评审", {...}); return; }`。
- 判定：明确可接受的非阻塞项。触发条件罕见（连续 3 次空响应）；影响限于一条可手动删除的 MR 评论，无数据/安全影响；与已确认的「内存队列、无幂等」等边界同级。建议在上生产 webhook 前顺手修复。

### Low

**F-002：`normalizeRepositoryKey` 注释声称处理大小写，实现只做 trim**

- Severity: Low
- Evidence: `src/rules.ts:95-98` 注释写「去掉首尾空白与大小写差异」，实现仅 `value.trim()`；GitLab `path_with_namespace` 实际大小写敏感且来源一致，故行为上未出错，但注释与实现不一致，违反工程质量契约「运行行为、注释必须一致」。
- Failure scenario: 维护者依据注释认为规则键大小写不敏感，写出 `Team/App` 的规则却匹配不到 payload 的 `team/app`，需额外排查。
- Source requirement: engineering-quality「注释与实现一致」；`src/rules.ts` 为本次新增。
- Suggested fix: 删除注释中「与大小写差异」字样，或同时在 `normalizeRepositoryKey` 两侧做 `toLowerCase()`。

**F-003：gitlab-client 两个用例沿用默认 10s 重试间隔，套件拖慢约 40s**

- Severity: Low
- Evidence: `test/gitlab-client.test.ts:33-39` 与 `test/gitlab-client.test.ts:93-98` 未传 `retryDelayMs: 0`，其 fake 响应返回空 changes 触发 2×10s 真实等待；本轮 `npm test` 中这两用例各耗时 20022ms / 20016ms。
- Failure scenario: 测试套件随用例增长继续变慢，降低开发反馈速度；不影响功能正确性。
- Source requirement: 测试应快速、离线可重复（README「可离线运行」）。
- Suggested fix: `makeClient` 默认注入 `retryDelayMs: 0`，需要验证真实间隔的用例单独覆盖。
