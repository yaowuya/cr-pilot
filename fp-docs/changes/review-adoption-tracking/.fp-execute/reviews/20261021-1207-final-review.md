### High

#### F-001 生产仓储 `insert` 不返回自增 ID，建议明细在任何部署中都不会落库

- **Evidence:** `src/infrastructure/sqlite/review-record-repo.ts:65-86` 的 `insert(record)` 调用 `insertStatement.run(...)` 后直接结束，没有 `return`、也没有读取 `lastInsertRowid`；`ReviewRecordWriter.insert` 的返回类型是 `number | void`（`src/application/review-pipeline.ts:31-37`）。管线在 `review-pipeline.ts:517-527` 以 `const recordId = writeRecord({...}); if (recordId !== undefined) writeFindings(...)` 消费它，因此生产环境 `recordId` 恒为 `undefined`。
- **Failure scenario:** 真实部署中每条建议都不会写入 `review_findings`，`listPendingTracking` 永远为空，`getAdoptionStats` 返回全 0 且 `rate` 为 `null`。统计页长期显示「—」，追踪定时器每轮空转。测试之所以全绿，是因为 `test/application/review-pipeline.test.ts` 的 `findingWriterHarness` 用 `recordWriter: { insert: () => 1 }` 手动补了 ID，而 `review-record-repo.test.ts` 只断言写入内容，从未断言返回值。
- **Source requirement:** proposal What Changes 1「评审时持久化每条建议」；design D-002。
- **Suggested fix direction:** 在 `insert` 中 `const result = insertStatement.run(...); return Number(result.lastInsertRowid);`，并补一条仓储测试「insert 返回可用的自增 ID，且该 ID 能作为 `review_findings.record_id` 外键写入」。同时给管线补一条使用**真实**仓储（而非桩）的集成测试，防止同类装配缺口再次被桩掩盖。

#### F-002 webhook 的追踪分流在生产未接线，新提交仍会重复触发完整评审

- **Evidence:** `grep -rn "enqueueTracking" src/` 只命中 `src/interfaces/http/app.ts:24`（类型声明）与 `:100-101`（消费点）；`src/interfaces/http/server.ts:44-57` 的 `createApp({...})` 未传该依赖，`src/bootstrap.ts:243-260` 的 `startServer(...)` 也未提供。`src/interfaces/http/webhook.test.ts:15` 之所以通过，是因为测试自己传了 `enqueueTracking`。
- **Failure scenario:** 生产运行时 `deps.enqueueTracking` 恒为 `undefined`，`app.ts:100` 判空后回落到 `deps.enqueue(task)`，把 `eventKind="tracking"` 的任务送进完整评审队列。结果是每次推送新提交都重跑一次完整 AI 评审（浪费模型算力、重复回写评论），而追踪分支永远不会被触发。
- **Source requirement:** proposal What Changes 3；design D-004。
- **Suggested fix direction:** 在 `ServerDeps` 增加 `enqueueTracking` 并透传给 `createApp`；在 `bootstrap.ts` 注入实现（把 `{projectId, mrIid}` 记入待追踪集合，或直接触发一次追踪轮次），并补一条从 `startServer` 装配到 webhook 分流的端到端测试。

#### F-003 追踪器调用 GitLab 时未传实例地址与访问令牌，多实例与鉴权场景下必然失败

- **Evidence:** `src/application/adoption-tracker.ts:80` 调用 `client.getFileRaw(finding.projectId, finding.mrIid, finding.path, headSha)`，`:123`、`:127` 同样省略后两个参数；`gitlab-client.ts:117/95/66` 用 `gitlabToken` 直接写入 `PRIVATE-TOKEN` 头，传空串即无鉴权。`ReviewFinding` 表（`database.ts:85-110`）与 `review_records` 均未存 `gitlabUrl` / token。
- **Failure scenario:** 该服务的访问令牌来自 webhook 请求头 `X-Gitlab-Token`（`webhook-parser.ts:41`），不在全局配置里（`README.md:119`）。追踪器是脱离请求的定时任务，拿不到任务级 token，于是所有 `getFileRaw`/`getDiscussions` 调用都会以未鉴权身份发出并返回 401；`trackOne` 捕获后记为 `unknown`，全部建议长期停留 `unknown`，采纳率恒为 `—`。多 GitLab 实例部署时还会连错实例。
- **Source requirement:** design D-006（GitLab 能力补齐）、D-001（判定链路必须可运行）。
- **Suggested fix direction:** 在 `review_findings` 或 `review_records` 持久化任务级 `gitlab_url` 与访问凭据（凭据须加密或至少不与业务数据同表明文存放），追踪时随调用传入；同时补一个断言「追踪调用携带任务级实例与 token」的测试。若决定改用全局只读令牌，需在设计中显式登记该安全取舍。

### Medium

#### F-004 追踪只扫描 `pending`，已判定项永远不会被重新评估

- **Evidence:** `src/infrastructure/sqlite/review-finding-repo.ts:166-176` 的 `listPendingTracking` 固定 `WHERE outcome = 'pending'`；`design/backend.md` 状态章节写明「终态可被后续追踪覆盖（例如先 `ignored` 后又改代码）」，但实现没有对应的重扫条件，`tracked_at` 只写不读。
- **Failure scenario:** 研发先无视建议（记 `ignored`），两天后同一个 MR 又推提交把代码改了，该条永远不会从 `ignored` 变成 `adopted`。结果是采纳率系统性偏低，且「后补改进」这一最有价值的场景被漏统计，与设计声明的状态机不一致。
- **Source requirement:** design `状态并发与执行流程`「终态可被后续追踪覆盖」。
- **Suggested fix direction:** 将扫描条件改为「`pending` 且（`tracked_at IS NULL` 或 `tracked_at` 早于该 MR 最近一次提交时间）」，用 `head_sha` 或提交时间做判据；补一条「已 ignored 的项在新提交后重新判定为 adopted」的测试。

- **Failure scenario:** 无运行时错误，但读者会误以为读取的是该 MR 的合并后内容；实际上读的是该 head 下的仓库文件。多 MR 指向同一 sha 时行为正确，只是参数冗余且注释可能误导。
- **Source requirement:** 共享工程质量契约的「注释与实现一致」。
- **Suggested fix direction:** 去掉未使用参数，或在 JSDoc 中说明「iid 仅用于保持端口签名一致」；建议直接移除，避免误导。

## Blocking Items Before Archive

1. **F-001**：让 `review-record-repo.insert` 返回 `lastInsertRowid`，并补「真实仓储能写出建议明细」的集成测试。
2. **F-002**：把 `enqueueTracking` 从 `bootstrap.ts` 经 `server.ts` 接到 `app.ts`，并补装配测试。
3. **F-003**：让追踪调用携带任务级 `gitlabUrl` 与访问令牌（需先决定凭据存放方式并在设计中登记）。
4. **F-004**：让已判定项在出现新提交时重新评估，与设计状态机一致。
5. **F-005**：补齐视觉证据或明确接受人工核对结论，使 UI/E2E Gate 不再是 `BLOCKED`。

## Residual Risks / Notes

- 追踪会为每条建议增加 GitLab 读取调用；当前实现按 MR 缓存文件内容，但未对轮次总量限流，建议上线后观察 429 日志。
- 历史数据无法补算：功能上线前的评审没有建议明细，统计起点为首次部署本版本之后。
- `getLatestHeadSha` 直接读 versions 接口而非复用对象方法，这一点在实现中已注明理由（解构调用时 `this` 不可靠），无需改动。

## Final Verdict Rationale

结构门禁通过、工作区干净、356 项测试与类型检查全部通过，说明实现可编译、可测试。但测试全绿掩盖了三处生产装配缺口：

**F-001** 是最根本的：`review-record-repo.insert` 不返回自增 ID，管线因此永远拿不到 `recordId`，建议明细在任何真实部署中都不会写入 `review_findings`。测试没抓到它，是因为管线测试用 `insert: () => 1` 的桩替掉了仓储。

**F-002** 同理：`enqueueTracking` 只在类型定义和 app 消费点出现，`server.ts` 与 `bootstrap.ts` 都没接线；测试自己传了依赖，所以没暴露。二者叠加的结果是「采纳追踪」这一核心能力在真实部署中完全不可用，且每次推送新提交还会重复触发完整评审。属于核心目标不可用，定级 High，判定 `FAIL`。

F-003 缺少任务级凭据会让追踪调用全部 401；F-004 与设计状态机不一致，会系统性拉低采纳率；F-005 使 UI/E2E Gate 为 `BLOCKED`。均须在归档前修复。
